# docs-tester's permission boundary

docs-tester needs more than the EC2FullAccess it started with: provisioning an SSM-reachable EC2 target also touches IAM roles and SSM Parameter Store, and applying Terraform needs to read/write its own state in the tfstate bucket.

We attach one customer-managed policy, `doc-testing-tool-terraform-policy` — not AWS-managed `*FullAccess` policies attached directly. Every resource-level statement is scoped by name prefix: IAM role/instance-profile actions to `role/doc-testing-tool-*` and `instance-profile/doc-testing-tool-*` (with `iam:PassRole` further conditioned on `iam:PassedToService=ec2.amazonaws.com`), S3 to `doc-testing-tool-tfstate-*`, SSM parameters to `/doc-testing-tool/*`, and `ssm:StartSession`/`SendCommand` to instances tagged `Name=doc-testing-tool-ec2`. EC2 itself has no per-resource tagging support at `RunInstances` time, so those actions stay `Resource: "*"`.

This means the EC2 target's IAM role/instance-profile names must be prefixed `doc-testing-tool-`, its `Name` tag must be exactly `doc-testing-tool-ec2`, and the SSM parameter must live under `/doc-testing-tool/` for the policy to actually grant access — these aren't arbitrary naming choices, they're load-bearing for the permission boundary.

**Corrected from an earlier draft of this ADR**: that draft argued against granting `s3:CreateBucket`/`DeleteBucket` on the grounds that "Terraform can't create a bucket and use it as its own backend in the same apply, so the permission doesn't buy anything." That's true for a single apply, but wrong as a reason to withhold the permission — another project's policy in this account grants exactly this, scoped to its own state bucket, because a two-stage bootstrap (create the bucket with local state, then `terraform init -migrate-state` into it) is a legitimate and already-used pattern in this account. `doc-testing-tool-terraform-policy` grants `s3:CreateBucket`/`DeleteBucket` scoped to `doc-testing-tool-tfstate-*` for the same reason: it keeps the bucket's entire lifecycle — not just its objects — inside Terraform and this one policy, rather than requiring a separate admin identity for bucket creation going forward.

**Three gaps only surfaced by actually running `terraform apply`, not by reviewing the policy statically** — static review (checking it against another project's policy) missed all three:

1. `aws_ssm_parameter` needs `ssm:DescribeParameters` (added to the `SsmDescribe` statement, `Resource: "*"` like its neighbors — this API doesn't support per-parameter resource scoping).
2. The document-scoped session/command statement listed `SSM-SessionManagerRunShell` and `AWS-RunShellScript` but not `AWS-StartPortForwardingSession` — the actual document `infra/tunnel.sh` uses. Added to the same `SsmSessionAndCommandsDocuments` statement.
3. Even with that document ARN added, `ssm:StartSession` for port forwarding still failed — splitting the instance-resource and document-resource permissions across two separate statements (the shape that already works for `SendCommand`/shell sessions) does not work for port-forwarding's `StartSession` call. AWS's own documented pattern for this case puts both the instance ARN and the `AWS-StartPortForwardingSession` document ARN in **one statement** with the same tag condition — added as a new `SsmPortForwardingOnDocTestingToolInstance` statement rather than reshaping the working shell-session statements.
