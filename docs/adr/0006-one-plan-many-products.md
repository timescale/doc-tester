# One plan declares its products; shared steps run on all of them

444 docs pages tag both `cloud` and `self_hosted` in frontmatter, 71% of the site, and until now a `<TestPlan>` could run on exactly one substrate. A both-tagged page could get a Cloud plan, a self-hosted plan, or two plans whose SQL steps were copies of each other. Copies drift, and drift between two descriptions of one procedure is the bug class this tool exists to catch. Checked on 2026-10-08: of the 35 plans in the corpus, one sat on a both-tagged page, and it covered Cloud only.

A run of a both-tagged page now proves the procedure on each product the page claims, with one verdict per product. The plan says which products it covers in a `target:` line before step 1 (`target: cloud, self-hosted`); a plan without one targets `cloud`, so nothing written before this line existed changes meaning. Steps are shared unless marked: a step prefixed `[cloud]` or `[self-hosted]` runs on that product only. In a two-target block only `run SQL`, the `expect` assertions, `fork the service` and `download` may go unprefixed, because only those mean the same thing on both sides. Console verbs exist only on Cloud, and `run command` runs on the tester's machine for Cloud but on the box as root for EC2, so an unprefixed one is a parse error rather than a guess (the same no-inference boundary as ADR 0004). A single-target plan allows no prefixes at all.

When the procedures diverge rather than the connection, or when a page imports a partial whose plan is Console-only and needs its own self-hosted coverage, a page carries more than one `<TestPlan>` block. Every block then needs its own `target:`, no two blocks may claim the same product, and coverage is their union. Rule of thumb for the author: if more than a third of the steps would carry a prefix, write two blocks.

The plan's claim is checked against the page's. A block targeting a product the page's `products:` does not list is a parse error, because the plan claims more than the page does. A page tagged with a product no block covers is a lint finding and a "not covered" cell in the batch summary, never a failure: it is the state of every plan on a both-tagged page written before `target:` existed, and the whole point of the line is to make that gap visible.

`fork the service` now means one thing, a throwaway copy of every target: a fork of the standing service on Cloud, a no-op on EC2 where every run is a fresh box (ADR 0005). `fork the self-hosted service`, which carried both "where" and "throwaway", is retired; the parser reports it with a pointer at `target:`. The 11 plans that used it and the dev fixture were updated in the same change. The parser knows `cloud` and `self-hosted` only; `mst` and `enterprise` are parse errors until a substrate exists, and adding one is a row in `TARGETS`, a provisioner and a walker, with no change to the grammar.

A run walks every product the plan declares by default, Cloud first, then EC2, serially, and a Cloud failure does not skip the self-hosted walk because the two verdicts are independent. `--products` narrows the set; asking for a product the plan does not declare skips the page with its reason, never grades it, because a run with no procedures would read as a pass. Step logs and screenshots carry the target in their name so two failures on one page never share a file. The page passes only if every product that ran passed.

Rejected: reading the products off frontmatter alone (ADR 0004's data still holds, and it would have turned every Console-only plan on a both-tagged page into a self-hosted failure the day it shipped); keeping the retired fork line as an alias (one grammar, one spelling, and only 11 plans to edit before anyone else is using the tool); defaulting a two-target plan to Cloud only (the verdict should cover what the page claims, and the EC2 cost is opted into per plan, not per run).

**Amended by ADR 0008:** the one-block-per-product rule becomes one block per (target, os), so a bare self-hosted plan can be written once per distro.
