# A bare plan names its path, declares its prerequisites, and waits as a reader would

ADR 0008 gave every Linux distro a plan, and ADR 0010 checks each against the reader's path. Both assumed the path is "Linux, then the distro tab", and that the only thing a bare box needs is an OS. The install page's Docker and Kubernetes tabs break both: they are top-level tabs (Docker has three sub-tabs, one with no commands at all), their guides say "you need Docker and psql" or "a cluster and kubectl" without scripting either, and a human's typing latency hides readiness races that a bot at machine speed hits. Nothing in this ADR is built yet; it fixes the design for #92 (Docker) and #90 (Kubernetes) so the pieces can land one at a time.

**`os:` names the box, and a new `path:` line names the reader's path.** Until now `os:` did both jobs, through `OS_TABS`. A Docker plan runs on an Ubuntu box and reads the Docker tab, so the jobs split. `path:` takes a key from a fixed table (`docker-ha`, `docker-light`, `kubernetes`), each mapping to a list of tab labels (`["Docker", "TimescaleDB-HA"]`). Absent means `["Linux", OS_TABS[os]]`, so no existing plan changes. The line is called `path:`, not `tab:`, because it names the reader's path (`CONTEXT.md`), and for a distro that is two labels. It is legal only with `machine: bare`, like `os:`. A label the page no longer has is an error, never a skip (ADR 0010). `lib/fidelity.mjs` stops hard-coding `["Linux", OS_TABS[plan.os]]`; `readerPath` already takes any list of labels.

**A run unit is `(target, os, path)`.** A Docker block and an Ubuntu block both run on Ubuntu, so a result row can no longer be keyed by distro alone. This amends ADR 0008's "one row per `(target, os)`". `--os` still narrows by distro.

**A plan declares its prerequisites with `needs:`, and the harness provides them.** A prerequisite (`CONTEXT.md`) is something the guide says you need and does not script. The tokens are `docker`, `psql` and `kubernetes` (a self-managed cluster plus `kubectl`, which a reader counts as one thing). The harness installs each over SSM after boot and before step 1, using the thing's own official installer, and the report lists what was installed with its version. A distro plan declares nothing, so its box stays bare and a distro guide that forgets the client still fails (Debian's partial installs `postgresql-client-18` explicitly, and that is worth keeping testable). The Docker the harness installs must work for the box's default user without `sudo`, because a Docker that needs `sudo` is not one a reader would call working. `needs:` is declared, never inferred from the page's prose (ADR 0004), and is legal only with `machine: bare`.

**A plan models reader latency with a `wait` verb, not a retry and not a pause.** A person takes seconds between `docker run -d` and `psql`; the container needs that long to accept connections. A bot would get `connection refused` and the run would go red for a reason no reader would see. The verb is fixed-vocabulary and names its subject and its limit, for example ``wait up to 90s for postgres in container `timescaledb` `` and ``wait up to 300s for pod `timescaledb-0` ready``. The name must appear on the reader's path, so a guide that renames the container makes the wait stale and the lint says so. The lint treats `wait` like `answer`: it runs nothing the reader runs, so it is not a "command not on page", but it is checked for the name. A `wait` that runs out of time fails the step, with the probe's last output. The report shows how long each one waited.

**Kubernetes runs on k3s on the same bare Ubuntu box, not a managed cluster.** The guide's prerequisite text lists "Self-managed Kubernetes" first, the commands under test (`kubectl create namespace`, the PVC, the StatefulSet, the secret) are core API calls that do not depend on the cluster being managed, and a managed cluster means widening `docs-tester`'s policy (ADR 0003, admin work only the user runs), a reaper for a forgotten cluster (ADR 0005 deliberately has none), and 20 to 45 minutes a run. A managed cluster is taken only on evidence, if a drift appears that k3s cannot reproduce. #90's scope text is amended to say so. The honest cost: the storage class, load balancers and image-pull behaviour differ from a managed cluster, and the guide's PVC uses the default storage class.

**Docker: one block, for HA.** `TimescaleDB-HA` is the primary path. `TimescaleDB light` is the same shape with another image and is a mechanical second block once HA is proven. `Chainguard` has no commands, so it is "nothing to test", listed and not failed. Under ADR 0010 every shell-fence command on the HA path is run or `skip`ped, including the `127.0.0.1` variant that reuses the container name `timescaledb` (it needs `skip`, since it conflicts with step 2) and `docker exec … psql`.

**Untagged fences: fix the docs, and warn until then.** Found in step 1, by running the lint on the real Docker tab: `docker pull` and the main `docker run` are in code fences with no language tag (four of them, two on the HA tab and two on the light tab), and ADR 0010 reads only `bash`, `sh` and `shell` fences. The lint therefore could not see the two commands the Docker plan exists to test. The fix belongs in the docs: tag them `bash`, like every other command on the page. Until the docs are fixed the tool does two things, neither of which relaxes the exact-equality contract. A plan that runs a command the page gives only in an untagged fence gets its own finding, `command in an untagged fence`, instead of the misleading "command not on page", and `test-page` refuses it as it does any drift. And an untagged fence on the reader's path that looks like a command and that the plan neither runs nor `skip`s is listed as an advisory by `lint-plan` and as a warning by `test-page`, so the lint cannot pass over it in silence. "Looks like a command" is a heuristic with a known ceiling: the first word is one the page's own shell fences start a command with, or one of a short list (`sudo`, `docker`, `kubectl`, `psql`, …), so a fence of sample output is not listed. A `skip` of such a command is not stale; it is how a plan says it knows.

**Considered and rejected:**

- *Treating every untagged fence as shell.* One line, but a fence of sample output with no tag would then be a command the plan must run.
- *Reading untagged fences when their first word is a known command, as a rule instead of a warning.* It adds a list to maintain and makes the contract depend on it. The same list is used here only to decide what to warn about.
- *A free-text `tab:` with the page's labels.* Flexible, but a typo only fails at lint time and the plan drifts from the page's spelling. The fixed table matches how `os:` works.
- *Inferring the path from the plan's commands.* ADR 0004: explicit, never inferred.
- *Preinstalling Docker and `psql` on every bare box.* It would hide a distro guide that forgets the client.
- *Prerequisites as plan steps.* Their commands are not on the page, so the lint's "command not on page" fails them.
- *Pinning prerequisite versions.* Reproducible, but the pins go stale unnoticed, and a guide failing because Docker changed is something a reader would hit too. Versions are recorded in the report, and pinned only if runs turn flaky.
- *A baked AMI with the prerequisites.* Fast, but it is admin work only the user runs, and a baked box drifts toward the preinstalled target ADR 0007 exists to avoid.
- *A pure delay (`wait 15s`) or a retry-on-failure.* A delay is a guess against an image pull of unknown size, and a retry hides real failures.
- *A managed cluster for Kubernetes now.* See above.

**Assumed, not asked, and open to change:**

- The exact spelling of the `wait` verb and its two starting probes. Settled in step 3 for the first (below); the `pod` spelling and its `kubectl` probe wait for step 4, when there is a cluster to run it against.
- `wait` takes its limit in the verb, in seconds, with no default.
- `needs:` is not checked against the page's prerequisite prose. That prose is not deterministically extractable.
- A Docker plan's `os:` is `ubuntu`.

**Built (2026-10-16, step 3: `wait`).** ``wait up to Ns for postgres in container `name` `` is bare-only, with a limit of 1 to 600 seconds and no default. A name with a space, a pure delay (`wait 15s`) and a retry do not parse, so they are reported `unparsed` like any unknown line. The walker runs one script on the box as the default user, polling every second: ready is `pg_isready -h 127.0.0.1` inside the container (over TCP, because an image that initialises on a temporary server would otherwise be called ready early), and the report says how long it waited. A container that does not exist, or has exited, fails at once with its own log (`docker logs --tail 12`), not after the limit. The lint checks that the name is a whole word on the reader's path, and a `wait` is not a "command not on page". The pod form is not built.

**Decided (2026-10-16, after step 3: the data folder, the assertion, the end of the session).** Found while running the Docker plan, settled in a grilling session:

- *The data folder is a guide gap, not a prerequisite.* The guide's `-v <folder>:/pgdata` fails on a folder that does not exist, and the guide never says to create it. The plan runs the guide as written and goes red there, like Debian and Fedora, and `wait` says why at once with the container's log (`Waiting for permissions on /pgdata`). Providing the folder with a `needs:` token was rejected: it would turn the plan green over a guide bug and hide it from anyone who reads only a green row. `CONTEXT.md`'s "Prerequisite" now says so. The cost is that `psql`, `\dx` and the assertion never run against the real page until the docs say to create the folder, so their coverage lives in `dev-fixtures/.../docker-dev.mdx`, the Docker flow plus the `mkdir`, labelled as the one place that deviates. It is the same device as the other `-dev` fixtures. The docs owner is told once, in a single message that also covers the four untagged fences.
- *A Docker plan asserts with ``expect output contains `text` ``.* It checks the transcript of the `run command:` above it, once that command has exited. It is a plain case-sensitive substring, never a regex. `expect rows:` was not extended: it goes through the SSM tunnel with the box's generated password, the guide's is the literal `password`, and asserting through a different route than the reader's would check the database and not what the page says the reader sees. The lint ties the text to the page two ways: it must be in a non-shell fence on the reader's path (`asserts text the page never shows`), and it must not be text the plan types for that command (`asserts text the plan itself types`; a terminal echoes what is typed). Known ceilings: a `sql` fence holds typed input as well as sample output, so "non-shell fence" approximates "sample output"; the driver keeps only the last 80 lines or 6000 characters of a transcript; and a substring is satisfied by a longer string that contains it (`timescaledb` by the `timescaledb_toolkit` row), so the Docker plan asserts on the extension's own description line instead.
- *A psql session the guide never ends is ended with ``answer `postgres=#` with `<Ctrl-D>` ``.* The Docker guide never tells the reader to leave psql (it says "Press `q` to exit the list"), and a `\q` answer is `command not on page`. Without an end the session sits at its prompt until the driver's idle timeout fails the step. `<Ctrl-D>` is a key reply like `<Enter>`: declared in the plan, typed by the driver without a trailing Enter, and exempt from the lint because it is not a command a reader types. A harness that closed the session silently was rejected, because the asymmetry between a bot and a reader is declared in the plan (ADR 0007), and a `\q` exemption was rejected because it loosens the lint for a command no reader types.

**Decided (2026-10-20, the Kubernetes harness: a grill of ten questions).**

- *`needs: kubernetes` provides a cluster the reader's `kubectl` can reach.* Ubuntu only, like `docker`. The harness installs k3s from its stable channel, then the upstream `kubectl` at the server's version (checksum-verified, replacing k3s's symlink by rename), and puts the kubeconfig in the default user's `~/.kube/config`. The probe, as that user, is `kubectl get nodes` showing a Ready node, and the report lists `k3s vX, kubectl vX`. Versions are recorded, not pinned, as for Docker.
- *The kubeconfig is a prerequisite, not a guide gap.* The page's "a cluster" and "kubectl for command-line interaction with your cluster" are one prerequisite, so the connection between them comes with it. A turnkey-cloud reader gets theirs from the provider. `CONTEXT.md`'s "Prerequisite" says so.
- *The `pod` form is ``wait up to Ns for postgres in pod `NAME` ``,* not the ``pod `name` ready`` spelling deferred above, because pod Ready is observed to come before postgres. It polls `pg_isready -h 127.0.0.1` through `kubectl exec` once a second, counted in sleeps like the container form, with the same 1 to 600 s bound and bare-only. It fails at once, with the pod's `describe` and log tail, if the pod is missing or its container has terminated. The namespace is the reader's current context's. The page's plan uses 300 s, which leaves room for the image pull.
- *The pod name is checked as `NAME-N`,* where `NAME` is a whole word on the reader's path and `N` is an integer, because the page names the StatefulSet and never the pod. Ceiling: the ordinal is not checked against `replicas`, so `timescaledb-7` passes the lint and fails at the probe.
- *A plan keeps a manifest's indentation.* A `run command:` body keeps its lines' relative indentation (only the common leading indent is stripped), and the lint compares heredoc bodies the same way.
- *A fence not tagged as shell whose first command word is a known one (`kubectl`) is reported,* as untagged fences are, with the fix "tag the fence `bash`". The Kubernetes plan therefore stays lint-red on the `yaml`-fenced steps until the page is retagged, as Docker was before #647. That request goes to the docs owner later, separately.
- *A page's heredoc terminator that is not at column 0 (after the fence is dedented by its own opening indent) is a new guide finding,* "heredoc never ends as shown". `<<-` with leading tabs is exempt. Without it the Kubernetes plan goes green over the guide's bug, which the data-folder decision refused to do. Same ceiling as #647: it reads MDX source, and rendering is unchecked.
- *Known ceiling: the app pod's crash is invisible to a plan run.* After step 6 the page promises nothing to assert, and `expect output` must tie to text the page shows. A generic "no pod in Error" check was rejected: it would fail guides that legitimately show transient states, and it would assert what the page never promises.
- *Two PRs.* 4a is the grammar and lint (indentation kept, non-shell command fences reported, the terminator finding): no AWS, and it would have caught the Deployment's `EOF` on the page today. 4b is `needs: kubernetes`, the `pod` form of `wait`, a Kubernetes plan on a scratch copy of the real page, and a real-box run with negative controls, including `kubectl exec -it` through the pty driver. 4b waits on 4a, because the plan needs its indentation preserved to carry a manifest.
- *The probe is not merged.* Its branch stays local until 4b's real-box run re-proves the same facts through the real harness, and is then deleted. Cost: the exact commands behind the probe runs are not in the repo.

**Decided (2026-10-20, during step 4b: a wait for a pod that runs no postgres).** The first box run of the Kubernetes fixture failed at the guide's `kubectl exec -it test-pod` with `container not found ("test-pod")`: a bot reaches it seconds after `kubectl run`, and a reader never would. The postgres form cannot wait for `test-pod`, which runs `sleep infinity`, so there is a second form, ``wait up to Ns for pod `NAME` ready``, meaning the Kubernetes Ready condition. For a pod with no postgres, Ready means running, which is what a reader waits for. It is a different action from the postgres form and never `exec`s into the pod, and it is checked by the lint with the same name rule. This reverses the grill's dropping of the `pod ... ready` spelling only for pods that run no postgres: the reason for dropping it (pod Ready comes before postgres is up) is why the postgres form does not use it. A plain `run command: kubectl wait ...` was rejected because the page does not give it, so the lint would call it `command not on page` and the real plan would stay red for the wrong reason.

**Built (step 4b).** `needs: kubernetes` (Ubuntu only): `lib/prerequisites.mjs` installs k3s from a downloaded installer (`curl | sh -` would run an empty script, and succeed, when the download fails), then the upstream `kubectl` at the server's version with its sha256 checked, replacing k3s's symlink by rename, then the default user's `~/.kube/config`; the probe, as that user, waits for a Ready node and records `k3s vX, kubectl vX`. A probe is now a script file run as the default user, because a `$(...)` inside a `bash -c "<string>"` is expanded by the shell that receives it, and `provide()` takes an injectable `send` so this is tested without AWS. The pod forms of `wait` share one loop in `lib/wait.mjs`. `scripts/check-needs-kubernetes.mjs` and `scripts/check-wait-pod.mjs` run the installer and both scripts against fakes, and each was checked by breaking it (the installer in five ways, the pod wait in five and the Ready form in six) and watching the matching check fail. `dev-fixtures/docs-repo/src/content/docs/self-hosted/kubernetes-dev.mdx` carries the guide's flow with its deviations labelled, as `docker-dev.mdx` does.

**Consequences.**

- The plans themselves go on the real page, in the same file as Tiger-Data-Docs #645 (merged 2026-10-20). While it was a draft they were tested on a scratch copy of the real page, kept outside `dev-fixtures/` so it is treated as real docs (ADR 0010).
